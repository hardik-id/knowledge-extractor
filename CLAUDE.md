# Knowledge Extractor

A Next.js 16 (App Router, Cache Components) UI for a document pipeline:
**Select files → Ingest → Transform → Classify → Enrich → Extract → Index**.

## Design system: Polder

- Rules: `design/DESIGN.md`. Component guidelines: `design/components/*.md`. Values: `design/tokens.json`.
- Code uses the tokens through `src/app/globals.css` (CSS variables plus Tailwind utilities such as `bg-surface-tint`, `text-ink-heading`, `text-link`, `bg-action`).
- **Never use raw hex or Tailwind palette colours** (`text-blue-600`) in components. If a colour is missing, add a token to `design/tokens.json` and `globals.css` in the same change, with light and dark values that pass 4.5:1.
- One primary (orange) button per view. Status always pairs an icon with a word.
- The app follows "Polder for apps" (`design/DESIGN.md`): 1px hairlines instead of frames, shadows (`shadow-float`) only on what floats, radii `rounded-control` (4px) / `rounded-panel` (6px) / `rounded-pill`, controls 32px (`h-control`; `h-control-lg` 36px for a page's main actions), Inter. Type steps are named utilities, not raw sizes: `text-title`, `text-section`, `text-body`, `text-small`, `text-caption`; never `text-[13px] leading-[18px]`. Buttons: `default` is the one orange primary, `secondary` (or `outline`) a neutral border, `ghost`, and `destructive` (filled) only at the confirming step. The focus ring is one rule in `globals.css`: components don't set their own. `src/components/ui` takes tokens only (`ui-rules.test.ts` checks it); `design-tokens.test.ts` checks `tokens.json` against `globals.css` and the contrast of every pair.
- Breakpoints are Polder's: `sm` 600px, `md` 960px, `lg` 1280px (they override Tailwind's defaults).

## Apps and branches

- One shell hosts several apps by route; a dropdown in the shell switches between them. `src/apps/registry.ts` lists them (id, name, description, href, `experimental`) and `appForPath(pathname)` finds the app a URL belongs to; icons are in `src/apps/icons.ts`. `components/layout/app-shell.tsx` is app-agnostic (`nav`, `mobileNav`, `navLabel`, `skipLabel`); each app's layout fills it.
- `NEXT_PUBLIC_APPS` (comma-separated ids, in the order to offer them; default every app) chooses which apps a deployment offers, checked in `config/env.ts`. `registry.ts` exports `ALL_APPS` (everything the code has) and `APPS` (the offered ones: the switcher, `appForPath`, `FIRST_APP`). `/` redirects to the first offered app (`next.config.ts`). With one app the switcher is a plain mark and name, and `proxy.ts` answers "not found" for the routes of an app that is not offered. Test code against `offeredApps(ids)` and the `apps` argument of `appForPath` / `isHiddenAppPath`, not by changing the environment.
- Each app has its own routes (`src/app/(apps)/<id>/`, a route group: its layout puts every app behind sign-in, and the URLs don't include `(apps)`), its own run store (`RunStoreProvider` in its layout) and its own folder for app-only code (`src/apps/<id>/`). Anything two apps both need is a shared component (`components/`, `features/file-picker`, `features/extraction`), not a copy and not an `if` on the app. Adding an app: an entry in the registry and the icon map, a route folder in `src/app/(apps)/` with a layout, a store, and a proxy matcher only if it needs one.
- Apps: **Knowledge Extractor** (`pipeline`, `/pipeline/[stage]`) and **Knowledge Studio** (`studio`, `/studio`, experimental): extraction only, over enriched Markdown documents in a storage container. Its documents come from `services.documents` and `catalog.list("storage")`; extraction reads the document by the run file's `sourceRef` and keeps its ETag as `sourceEtag`. What the backend has to provide is in `docs/studio-api.md`.
- Studio works in **workspaces**. A workspace is a name and a description on a run, and the run holds the rest: the documents, the extraction configuration (saved versions, each with an optional note; restoring an old one saves it as the next version), the conversation with the assistant, and the records with their reviews. All of it lives on the server (`services.workspaces`, then the run's own endpoints), so a workspace comes back the same in a new tab or another browser. The mock keeps workspaces and their runs in localStorage (`knowledge-extractor:mock-workspaces`): they survive a closed tab, not cleared site data or another browser. In the browser Studio keeps only the active document and source tab, per workspace, in sessionStorage. Applying or dismissing an assistant proposal is only remembered on the page; after a reload, a proposal that would change nothing shows "Already in what you have".
- Studio's addresses: `/studio` (the workspaces, last activity first, with "New workspace", Edit for the name and description, and Delete), `/studio/workspaces/[id]` (one address: a workspace with no documents shows the picker as the whole screen, "Use N documents" sends them to the run with `runs.setDocuments`; with documents it shows one working screen, no tabs). `/studio/workspaces/[id]/extract` redirects to it. The address decides the workspace and so the run: an unknown workspace, or someone else's, shows "This workspace no longer exists". Later changes to the documents go through "Add or remove documents" in the document switcher, a sheet; taking out a document whose records a person reviewed asks first.
- The working screen: one top bar (logo, "Workspaces", the workspace menu, the document switcher, a "Document | Output" switch hidden while the configuration is empty, the version text, "Assistant", the one Run button, "More", theme, account), the open document on the left with its highlights and the record strip pinned under it (one line per field of the current record, with the value and its actions, a "worked out" tag on fields that are not exact quotes, and a chevron that folds it), and one column on the right: a "Configuration" row, closed on a first visit (open or closed is remembered in the browser; it opens by itself only when a save is refused because of a problem in the configuration and on "Review" on a suggestion's card), which holds the record type, "What to extract", Chunking and the field table when open, and under it the assistant, always open (its header with the menu, the conversation, the input at the bottom). Below 1100px the column is an overlay opened by "Assistant". Selecting a field in the table keeps its highlights at full strength and fades the others. A suggestion is a card under the assistant's message (`suggestion-card.tsx`; the changes in plain words from `suggestionLines`, at most eight and then "and N more"; "Keep all", "Discard", "Review"; decided, it reads the outcome and has no buttons). "Review" opens Configuration and puts the focus in the table, where the suggestion is also shown (a bar with "Keep all" and "Discard all", new fields as rows, changes as lines under a row, a new record type as its own table). A template chosen on the start panel is offered the same way, as a card at the end of the conversation (`offerProposal`). With nothing saved and nothing drafted, and no proposal showing, the row reads "Nothing configured yet" and the conversation's empty state is the start panel. Review happens on the highlights and in the strip, which shows the whole record; there are no record cards.
- View only: the working screen follows the workspace's `permissions` through `useMay(permission)` (`src/features/iam/use-may.ts`, re-exported from `src/apps/studio/use-may.ts`; not loaded yet answers no; no component looks at a role's name). Without `workspace.edit` the top bar shows a "View only" tag and offers no Save, Discard changes, Restore, "Add or remove documents" or "More"; Configuration is text (`read-only-fields.tsx`, `readOnly` on the record type bar, prompt line and chunking row); the assistant has no input and no "Clear conversation", a suggestion card has no buttons; empty states say "No conversation yet." and "This workspace has no documents yet.". Without `workspace.run` there is no Run button and no "Generate". Controls are hidden, never greyed out. A 403 `forbidden` reported through `toastFailure` makes the open workspace be read again (`follow-refusal.ts`). Part 2 (record strip, value menu, workspace menu) is separate. In browser tests `giveRole` (`e2e/support/roles.ts`) gives a second person a role through the API; see `e2e/view-only.spec.ts`.
- Studio's code is in `src/apps/studio/`: `workspaces-entry.tsx` (the list), `workspace-row.tsx`, `workspace-facts.ts` (the facts under a workspace, and what deleting it removes), `workspace-form-dialog.tsx` (new and edit), `delete-workspace-dialog.tsx`, `workspace-scope.tsx` (opens the workspace the address names), `workspace-top-bar.tsx` (the one bar of a workspace; there is no sidebar under a workspace; addresses and rules in `nav-steps.ts`), `top-bar/` (the document switcher, version menu, Run button and "More" menu with their rules), `working-screen/` (the working screen: `one-screen.tsx`, `screen-state.ts` and `screen-provider.tsx` for what is selected, `document-pane.tsx`, `output-pane.tsx`, `record-strip.tsx`, `field-column.tsx`, `assistant-dock.tsx`, `use-proposal.ts` and `proposal-table.tsx`), `start/` (the start panel for an empty configuration), `studio-panel.tsx` (the page header and body of the workspaces list, like StagePanel without "Stage N of M" or footer), `documents-picker.tsx` (rules in `documents-change.ts`), `documents-screen.tsx`, `documents-sheet.tsx`, `extract-page-content.tsx` (loading and error states, then the working screen). The top bar and the screen share the Document/Output view, the Assistant overlay and the "Assistant" request through `ScreenControlsContext` (`screen-state.ts`).
- Next.js (Cache Components) keeps up to three pages it navigates away from, hidden with their state, and shows them again on the way back. Studio has one store, open on one workspace, so a hidden page can be showing another workspace's store when it comes back: it must read the workspace from the store. The workspace list starts over each time it is left (`workspaces-entry.tsx`), so it never shows an old order or old facts. - Trunk-based: everything merges to `main` through short-lived branches (`studio/<topic>` for studio work). Experiments live in `main` as their own app; dropping one means deleting its registry entry, its routes (`src/app/(apps)/<id>/`) and `src/apps/<id>/`.

## Sign-in

- Microsoft Entra ID, in the browser: `@azure/msal-browser` v5 (authorization code flow with Proof Key for Code Exchange, by redirect). The token is kept in `sessionStorage`, one sign-in per tab. The Next.js server takes no part. What the backend must set up and check is in `docs/auth-api.md`: keep it in step.
- `NEXT_PUBLIC_AUTH_MODE`: `none` (default, no sign-in; the dev token works in http mode), `entra` (sign-in for every app; needs `NEXT_PUBLIC_ENTRA_TENANT_ID` and `NEXT_PUBLIC_ENTRA_CLIENT_ID`; `NEXT_PUBLIC_ENTRA_API_SCOPE` is optional and defaults to `api://<client-id>/access_as_user`), `fake` (a pretend account for local checks; production builds refuse it). It is independent of `NEXT_PUBLIC_BACKEND_MODE`, so it works with the mock. A production build with `http` and without `entra` fails at build time.
- One app registration serves the UI and the backend. The UI sends the access token on every call as `Authorization: Bearer …`. The backend reads the person from the claims and applies its own permissions; there is no on-behalf-of exchange. Sign-in returns to `<origin>/auth/redirect`, sign-out to `<origin>/`.
- Code: `src/app/(apps)/layout.tsx` puts every app behind sign-in. With sign-in on it also renders a request-time marker (`await connection()` in `<Suspense>`): the gate keeps pages out of the prerendered HTML, and without the marker Next.js refuses to build `/pipeline/[stage]`, whose title depends on the URL. Check a change to that layout with a build in `entra` mode (placeholder ids are enough). `src/app/auth/redirect/` is outside the group: the page Microsoft returns to, which only runs MSAL's redirect bridge.
- `src/lib/auth`: `auth-client.ts` is the interface (`AuthClient`); `msal-auth-client.ts` implements it (the only file that imports MSAL, loaded on demand); `fake-auth-client.ts` is the pretend one; `auth-token-provider.ts` adapts a client to the HTTP client's `TokenProvider`; `auth-controller.ts` holds the rules, with pure helpers in `auth-state.ts`.
- `src/services/auth.ts` builds the client from the settings. Import `authClient`, `authSession` and `clearLocalData` from `@/services`. `src/features/auth`: `auth-provider.tsx`, `auth-gate.tsx`, `sign-in-screen.tsx`, `session-ended-dialog.tsx`, `user-menu.tsx`.
- With no session in the tab the app goes to Microsoft once, automatically. After a sign-out or a failed attempt it shows the sign-in screen and waits for the button (a flag in `sessionStorage`), so a broken setup can't loop.
- The account is the one the sign-in returned, never a pick among several cached ones.
- A call still refused after a token refresh (a 401) means the session has ended, decided once for the whole app: the token provider tells `appSession` (`src/lib/auth/session-signal.ts`), the one fact everything else reads. In `entra` and `fake` the app stays mounted under the session-ended dialog, and signing in again happens in a separate window so unsaved work is kept. In `none` (a dev token, development builds only) `features/auth/dev-token-dialog.tsx` is the same kind of dialog: it says the token is no longer accepted, names `make token` in the backend repository, and takes a pasted token (`DevTokenProvider` in `lib/auth/dev-token-provider.ts`: used at once, kept in the tab's `sessionStorage`, which is acceptable only because it is a local dev token and `devTokenAllowed` is false in a production build). The dialog is loaded only when `process.env.NODE_ENV` is not "production", so a production build does not contain it.
- While the session has ended it is quiet: `useAsyncData` treats a 401 as "still loading" and runs the load again when the session resumes; the store keeps why a workspace or run failed to load (`workspaceError`, `runError`) and the pages wait the same way and never say "the server didn't answer" for a 401 (`describeApiError` words the other causes); action failures go through `toastFailure` (`features/auth/report-failure.ts`), which says nothing for a session that has ended; the socket asks for no tickets and does not reconnect (`blocked`/`onUnblocked` in `lib/realtime/socket-client.ts`) until the person is back. New loads use `useAsyncData` or `useOnSessionResumed`, new failure toasts `toastFailure`, so they follow the rule.
- A token that can't be renewed because the network is down fails the call ("Can't reach the server"). It does not sign the person out.
- Sign-out, and a different person signing in, clear both apps' run stores and the mock's stored runs. Sign-out also signs out the person's other tabs.
- In `fake` mode, `window.__auth.expire()` in the console acts out an ended session.
- With sign-in on, open the app at `http://localhost:3000`, not the WSL `172.x` address: Microsoft only accepts http for localhost, and MSAL needs a secure context.

- `src/components/pipeline`: reusable stage building blocks (StagePanel, StageFooter, FileList, SplitView, MarkdownViewer, EmptyState, StageStatusBadge).
- `src/features/stages/markdown-stage-panel.tsx`: the file list and rendered document shared by Transformation, Classification and Enrichment. Each of those panels only passes its stage id and wording. `MarkdownViewer` shows YAML front matter as a properties block (`lib/front-matter.ts`, `components/pipeline/document-properties.tsx`).
- `src/features/file-picker`: `FileBrowser` (source tabs, search, list, select all) and `SelectionSummary`, shared by the pipeline's Select stage and Knowledge Studio. They take the sources, the noun and the search hint as props; the selection lives in the store.
- `src/features/extraction`: the extraction workspace of the pipeline app, three tabs (Studio composes the same parts on its own screen). `use-extraction-run.ts` holds the definition, the tab and `run()`; `extraction-actions.tsx` (Publish, Run) and `extraction-workspace.tsx` (loading and error states, the tabs) take its result, so a host places them in its own frame (the pipeline's is `features/stages/extract/extract-panel.tsx`). Define edits the extraction definition (`use-extraction-definition.ts`, pure rules in `definition-draft.ts`). "Templates" on the Define tab opens `template-dialog.tsx`: the picker, what the template brings, what changes against the editor, and what the next run does to the records (`template-impact.ts`); using one replaces the draft (unsaved) and the save note starts with "From template: <name>" (`template-note.ts`), until the draft is back to the saved version. Each record type's fields are one `<table>` (`field-table.tsx`): a row per field, tick boxes for Exact quote (`mode`) and Several values (`multiple`), the key behind the row's menu (shown by itself when edited by hand or wrong), and the rows stack by their own container width, not the window's. Review shows the extracted values as highlights on the document beside the list of records (`review-tab.tsx`, `review-marks.ts`, `records-pane.tsx`, `components/pipeline/annotated-text.tsx` and `annotated-markdown.tsx`). Output renders the records (`lib/output-template.ts`). Label colours are the `label-1` to `label-6` tokens, assigned in `labels.ts`. Records are changed through `useExtractionActions` in `features/run/use-extraction.ts` (the server's answer becomes the new state; nothing is optimistic). Selecting text to label it goes through `lib/dom-selection.ts` and `selection-menu.tsx`. The assistant chat is `assistant-panel.tsx` with `use-assistant.ts`; its messages live in the store, arrive as live events and are kept with the run ("Clear conversation" removes them).
- `src/components/ui`: shadcn/ui primitives, re-skinned. Add more with `npx shadcn@latest add <name>`.
- `src/store`: a Zustand store per app, built from slices (navigation, files, run, workspace). `pipelineRunStore` comes from `createRunStore(key)`: only its run id, selection and proceeded stages are persisted to sessionStorage. `studioRunStore` comes from `createWorkspaceRunStore(key)`: `openWorkspace(id)` loads the workspace, then its run, and the selection is the run's files; nothing of the run is persisted, only the active document and source tab, per workspace. `<RunStoreProvider store firstHref>` (in each app's layout) puts one in context and runs its hydrator and `<RunSync>`; `usePipelineStore(selector)` and `useRunStoreApi()` read the current app's store and throw outside a provider. Read derived state through `store/selectors.ts`; the pure rules behind it are in `store/run-state.ts`.
- `src/services`: the boundary to the backend. `contracts.ts` is the interface; `http/` (Django) and `mock/` (in the browser) implement it; `index.ts` picks one from `NEXT_PUBLIC_BACKEND_MODE`; `errors.ts` turns error codes into sentences. Import `services` from `@/services`, never an implementation. `services.access` (`access.ts` the types, `http/access.ts` + `http/access-parsers.ts`, `mock/mock-access.ts`) reads and changes who has access: tenants, tenant and workspace members, people, platform admins, activity (`docs/studio-api.md` section 9); no screen calls it yet.
- `src/features/iam`: who the person is and what they may do. `use-me.ts` is the one hook (`useMe()`; `me-store.ts` reads `services.me()` once when the app opens and again when the session resumes, in memory only), `permissions.ts` has `mayInWorkspace(workspace, permission)` (from the workspace's `permissions`) and `mayTestConnections(person)`. The browser never decides a permission: the API refuses, the UI only stops offering what would be refused, and no role is kept in `localStorage` or `sessionStorage`. "Test connections" is offered only to a platform admin (hidden, not disabled). In browser tests the default person is new and a member; `platformAdmin()` (`e2e/fixtures.ts`) is the dev issuer's shared platform admin, to be used only where one is needed.
- `src/features/run`: keeps the store in step with the run on the server (`run-sync.tsx`, `attach-run.ts`), plus the hooks and components panels share (`use-execute-stage.ts`, `use-stage-output.ts`, `stage-summary.tsx`, `connection-banner.tsx`).
- `src/lib/api`: the HTTP client and its middleware (request id, auth, retry, timeout, errors). `src/lib/realtime`: the reconnecting WebSocket. Neither knows about runs.
- `src/config/env.ts`: the checked `NEXT_PUBLIC_*` settings, the backend ones and the auth ones (see `.env.example`).
- `src/lib/auth`: sign-in without React (see "Sign-in"). `src/features/auth`: its React side.
- `src/lib`: pure helpers (`stages.ts`, `format.ts`, `utils.ts`) and generic hooks (`use-async-data.ts`, `use-debounced-value.ts`).

## How the UI talks to the backend

- **Commands by REST, state by snapshot, updates by WebSocket.** The browser never talks to NATS.
- A run is a set of files. For each file and each stage there is one **cell** (`pending | queued | running | succeeded | failed | stale`). A stage's status is derived from its cells; nothing stores it.
- Starting a stage only sends the request (`executeStage`). Progress arrives as cells, so never await the work.
- The snapshot is fetched again every time the socket opens, because updates sent while it was down are lost. For each cell the newer `updatedAt` wins.
- Transform's Markdown file is never changed by later stages. Classify writes a copy of it with front matter to a second container, and enrich updates that copy in place. So classify and enrich return the same text (`sharedOutputStages` in `contracts.ts`), and running classify again drops the enrichment.
- Extraction is driven by a definition (prompt, record types, fields that are an exact quote or inferred). Its result is records per file whose values carry spans into the enriched Markdown. Spans count Unicode code points, not string indices: convert with `lib/text-spans.ts`. The Rendered view maps text nodes back to the source with `lib/rehype-highlights.ts` and `lib/markdown-offsets.ts`. What the backend has to provide is written in `docs/extraction-api.md`: keep it in step with `contracts.ts`. Two rules to keep: an extraction run never replaces what a person added, accepted, rejected or edited (`services/mock/extraction-merge.ts`), and a value sent back unchanged keeps its origin and review.
- The app runs on the mock by default. The Django API (`hardik-id/knowledge-extractor-api`) serves what Studio uses (`docs/studio-api.md`), not yet everything the pipeline uses. If the mock and the real API disagree, fix `services/http` and `services/mock`, not the store or the panels.
- In mock mode, `window.__mockBackend` in the console can `dropConnection(ms)`, `failNext(stage)`, `unanchorNext()`, `lastExamplesUsed(runId)` and `setSpeed(n)`. The mock assistant understands a fixed set of requests (see `services/mock/mock-assistant.ts`).

## Backend status badge

- A badge in the top bar of every app (Studio's workspace bar, the shell's sidebar as a row right under the header, never at the bottom where Next's development indicator sits, and the mobile header) opens a panel with one row per part of the backend (`GET /api/v1/status`, `POST /api/v1/status/test`; contract in `docs/studio-api.md`, section 8). Code: `src/features/status/` (`status-rules.ts` the pure rules and words, `use-backend-status.ts`, `status-badge.tsx`), `services.status` (http, mock).
- Worst state wins: "Problem" (a real part failing), "Stub" or "Mock data", "Live". "Status unknown" when the backend answers 404 (the http service returns `null`: the panel says so, no toast). Development builds always show it; a production build only for a stub or a problem. The word hides below 600px, and in Studio's crowded workspace bar below 1600px (the icon, the accessible name and the tooltip stay). Status pairs an icon with a word.
- Loads when the app opens and each time the panel opens, never polled; "Live updates" follows the browser's own socket while a run is open. A part id the UI does not know is listed as its id in words.
- Tests: `npm run test:e2e:status` needs no backend (mock app on `E2E_PORT`, http app on `E2E_PORT + 1` whose API is a made-up host answered with `page.route`); `e2e/backend-status.spec.ts` is the one test against the real stack. The status load is one shared store (`status-store.ts`) for every badge; connecting and reconnecting sockets are "unknown", only a closed one is failing, and an ended session never turns the badge red. The visual specs mask the badge.

## End-to-end tests

- `npm run test:e2e` runs the suite (Playwright, Chromium only) in `e2e/`; `npm run test:e2e:ui` opens Playwright's UI mode. The backend stack must be up (`make up` in `knowledge-extractor-api`); without it the run stops at once with a line saying so. `npm run typecheck:e2e` checks the tests' types (the root `tsc`, ESLint's ignores and `npm run build` leave `e2e/` out of the app).
- The runner starts the app itself (`next dev` in http mode, Studio only) on `E2E_PORT` (default 3100) with its own build directory `.next-e2e`, so it never touches your `npm run dev` or its `.next`. Parallel runs, in different worktrees, each need their own `E2E_PORT`. `E2E_BASE_URL` tests an app that is already running and starts nothing. `API_DIR` is the backend repository (default: the sibling `knowledge-extractor-api`, also found from a worktree).
- The suite needs the backend's SCRIPTED assistant and extractor (the compose file's defaults). When the stack on port 8000 is set to a real model (`ASSISTANT_AGENT=openai`, `EXTRACTOR=llm` in the backend's `.env`), or someone is using it, give the tests a stack of their own instead of changing that one. In the backend repository: `ASSISTANT_AGENT=scripted EXTRACTOR=scripted ANTHROPIC_API_KEY= API_PORT=8100 DB_PORT=5532 REDIS_PORT=6479 OTEL_GRPC_PORT=4417 OTEL_HTTP_PORT=4418 docker compose -p ke-e2e up -d --wait` (its own database; `docker compose -p ke-e2e down -v` removes it). Then run the suite with `E2E_API_ORIGIN=http://localhost:8100 COMPOSE_PROJECT_NAME=ke-e2e npm run test:e2e`. Restarting a stack while a run is going fails that run with refused connections.
- Every spec imports `test` and `expect` from `e2e/fixtures.ts`. Each test gets a new person (`person`, a UUID `oid` and a dev token minted from the running backend; the token goes on every API request of the browser, so tests share no data and need no cleanup). `api` sets up data as that person without clicking (`api.createWorkspace(...)`). `contextFor(person)` opens a browser signed in as another person; make that person with `newPerson()`, which `fixtures.ts` re-exports (import it from there, never from `support/`). A console error, an uncaught exception or an API answer of 4xx or 5xx fails the test, unless it is declared with `expectApiError({ status, method?, path? })`.
- The first click after a navigation that opens a dialog or a menu goes through `clickUntilOpen` (`e2e/support/first-click.ts`; `openNewWorkspaceDialog` in `pages/studio.ts` uses it), never a bare `.click()`. In `next dev` the page can answer a click and then rebuild itself, throwing away what the click opened, which was the one flaky test. The helper clicks again until the dialog is open, focused and still there. No fixed sleeps and no raised timeouts as the fix. A production build is not an option for the suite: the app refuses to build against the real API without Entra sign-in.
- The working screen asks for the open document's extraction, which the backend answers with 404 before a first run: `fixtures.ts` expects that one answer in every test. `openOneScreen` and `ExtractionPage.open` (`pages/working-screen.ts`, `pages/extraction.ts`) open a workspace; below 1100px `openFields` opens the column's overlay. Configuration is closed on a first visit: `openOneScreen` and `openExtraction` make the browser remember it open (pass `{ configuration: "closed" }` for the first-visit screen), and `openConfiguration` opens it by hand.
- Find things the way a person does: `getByRole`, `getByLabel`, visible text. `data-testid` only where no role or label can name the element. Hidden pages stay in the DOM (see "Apps and branches"), so name the visible one by role.
- `e2e/accessibility.spec.ts` scans every main screen (the working screen in its Document and Output views, the start panel) with axe (WCAG A and AA, light and dark theme) through `expectAccessible` in `e2e/support/accessibility.ts`; a violation fails the test with the rule, page and element. Fix it in the app. Only what cannot be fixed here (a third-party component) goes on the short `EXCEPTIONS` list at the top of the spec, each entry with a link to an issue. A new screen gets a test there.
- A failing test leaves a screenshot and a trace in `test-results/` (CI: the trace on the first retry); the HTML report is in `playwright-report/` (`npx playwright show-report`). Neither is committed.
- `e2e/session.spec.ts` covers a refused token (401): a person breaks `person.token` (one character changed, declared with `expectApiError({ status: 401 })`) and the app must show the paste-a-token dialog once, with nothing else reporting it; putting the good token back and pasting anything into the dialog resumes, because the fixtures' header, not what is pasted, decides what the API sees.
- A UI change updates its tests in the same pull request.
- `e2e/visual.spec.ts` compares screenshots of a few stable screens (light theme, Chromium on Linux; baselines in `e2e/visual.spec.ts-snapshots/`, committed). A change that makes a screen look different fails it. When the change was meant, run `npm run test:e2e:update-snapshots` and commit the new pictures: the pull request shows the changed images, and the reviewer checks them. If the change was not meant, fix the code, not the baseline. Times and dates are masked, the threshold is small on purpose (see the spec), and new screens need the same stable data every run.

### The live suite (optional, never in the merge path)

- `npm run test:e2e:live` runs `e2e-live/` (the Playwright project `live`, only when `E2E_LIVE=1`, which the script sets). `npm run test:e2e` never runs it. It covers what the fast suite cannot: the real model answering in the assistant, and the real Microsoft sign-in. A spec that lacks what it needs is skipped, and the run prints the reason for each (`e2e-live/skip-reasons-reporter.mjs`). It starts an app only for a spec that will run. No trace, screenshot or video is kept.
- **Honest limit:** these specs were written on a machine with no model key and no tenant ids (backend #24, UI #37). They have never been run against a real model or a real tenant. Their selectors and waits come from the fast suite and the code, not from a live run: expect to adjust them the first time they run.
- **Real model** (`e2e-live/model.spec.ts`): set `E2E_LIVE_MODEL=1`, and start the backend with `ASSISTANT_AGENT=openai`, `LLM_MODEL`, and `OPENAI_API_KEY` (or `LLM_PROVIDER=azure`, `LLM_MODEL`, `AZURE_OPENAI_ENDPOINT` and `az login`), as in the backend's `docs/assistant.md`. It asks for the ADRs of `architecture-decisions-2026.md` and `platform-adrs.md` and checks the reply is a proposal that adds a record type named like an ADR or a decision, with fields (not the words). If the backend answers "No language model is configured", the spec skips. The key stays in the backend's own `.env`; it never reaches this repository.
- **Real sign-in** (`e2e-live/sign-in.spec.ts`): Microsoft's page is never scripted. A person saves a signed-in browser once:
  1. Register `http://localhost:<E2E_ENTRA_PORT>/auth/redirect` (a single-page application redirect address; the port is `E2E_ENTRA_PORT`, default `E2E_PORT + 1`) on the app registration.
  2. Start the backend with `AUTH_MODE=entra`, `ENTRA_TENANT_ID` and `ENTRA_CLIENT_ID` (backend `docs/auth.md`), so it accepts real tokens.
  3. Set `E2E_ENTRA_TENANT_ID` and `E2E_ENTRA_CLIENT_ID` (and `E2E_ENTRA_API_SCOPE` if the scope is not the default) in the shell.
  4. `npm run e2e:save-login`: it starts the app in `entra` mode, opens a headed browser and waits (5 minutes) while you sign in, then saves the state to `e2e-live/.auth/state.json`.
  5. `npm run test:e2e:live` (with the same variables) checks the name shows, the workspace list loads with the real token, and sign-out ends at the sign-in screen. Sign-out goes through Microsoft's sign-out page; if it asks which account, the spec does not click it for you.
- The state file holds tokens: `e2e-live/.auth/` is git-ignored, the file is written readable by its owner only, and nothing prints it, names a test after it or attaches it. Keep it that way: no tokens or keys in test names, logs, traces, or reports. A saved login expires; save it again.

## Adding a stage

1. Add its id to `STAGE_IDS` (in run order).
2. Add metadata in `features/stages/config.ts`.
3. Create `features/stages/<id>/<id>-panel.tsx` using `StagePanel`, and register it in `panels.ts`.
4. If proceeding needs more than `status === "ready"`, extend `canProceedFrom` in `store/selectors.ts`.
5. Give the mock a duration for it (`WORK_MS` in `services/mock/mock-backend.ts`). The run button comes from `useExecuteStage(<id>)`.

## Commands

- `npm run dev`: start the dev server
- `npm test`: unit tests with Node's own test runner (`src/**/*.test.ts`, no test library installed)
- `npm run test:e2e`: end-to-end tests (see "End-to-end tests")
- `npm run test:e2e:live`, `npm run e2e:save-login`: the optional live suite (see "The live suite")
- `npm run lint`, `npx tsc --noEmit`: run both before committing
- `npm run build`: also validates Cache Components rules
- `npx prettier --write .`: format the code
